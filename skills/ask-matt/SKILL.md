# 技能导航

你记不住每一项技能是正常的，拿不准就先来这里对一遍路。

注意：在评价某项技能做什么、或建议跳过某个步骤之前，先去读那项技能自己的 SKILL.md。这里的概述只负责指方向，不代替原文。

**流程**就是一条穿过各项技能的路径。绝大多数工作沿同一条**主流程**走，另外有两条**上匝道**并进来；剩下的技能要么独立使用，要么是垫在底层的词汇层。

## 主流程：从想法到交付

大多数工作走的路线：你有个想法，想把它做出来。

1. **grill-with-docs 技能**：用访谈把想法盘问锋利。只要你**在一个工作目录里干活**，就从这里开始——它是有状态的，会把学到的东西沉淀进 `GLOSSARY.md` 和 ADR 里。（没有工作目录时改用 grill-me 技能，见「独立使用」。两者底层跑的是同一个 grilling 技能；grill-with-docs 是会留下书面记录的那个，所以只要有仓库能承接记录，它就是更优选。）
2. **分支：所有问题都能在对话里敲定吗？** 如果某个问题非得跑起来才有答案（状态模型、业务逻辑、必须亲眼看到的界面），就绕道去做原型，两个方向都用 **handoff 技能**搭桥（原型放在它自己的目录里，这正是 handoff 的用途，见「阶段边界」）：
   - 用 **handoff 技能**把当前进展交接出去，针对交接文件开一个全新会话；
   - 用 **prototype 技能**以用完即弃的代码回答那个问题；
   - 再用 **handoff 技能**把结论带回来，在原来的想法讨论串里引用它。
3. **分支：这是跨多个会话的构建吗？**
   - **是** → 先用 **to-spec 技能**把讨论串变成规格说明，再用 **to-tickets 技能**拆成曳光弹式工单，每张写明自己的**阻塞边**。然后二选一推进：
     - 每张工单跑一次 **implement 技能**，**每做完一张就清空上下文**。本地跟踪器上就是 `.scratch/<feature>/issues/` 里每张工单一个文件，手工按阻塞优先的顺序推进；真实跟踪器上阻塞边是原生链接，阻塞项已完成的工单随时可抓来做。每张工单自包含，上一张的上下文用完即可丢。
     - **implement-spec 技能**一次跑完整份规格：它把工单读成一张**任务图**，让实现子代理并行跑遍已就绪的**前沿**，全部落到同一条**集成分支**上。想编排整个构建、而不是自己逐张驱动工单时用它。
   - **否** → 就在当前上下文窗口里直接跑 **implement 技能**。

   无论哪条路，代码都靠 **tdd 技能**驱动建成（一次一个红-绿切片），并以 **code-review 技能**收尾：对 diff 做双轴评审（规范 + 规格）。implement 技能会按工单分别跑这两样；implement-spec 技能的实现者各自驱动 tdd，最后在集成分支上跑一次 code-review。只想测试先行地做出一个具体行为、不需要完整规格时，单独用 tdd 技能；想针对某个固定点评审分支或 PR 时，随时单独用 code-review 技能。

   工作以 PR 形式提交时，**pr 技能**负责塑造正文：展示改动的最小可视化素材、证明有效的改动前后证据，并判断这是单向门还是双向门。它是模型调用式的，代理每次写 PR 时都会取用。

4. **retro 技能**收尾闭环。一次构建之后（尤其是走歪的那次），它回看会话，建议修改的是代理的**环境**而非代码：导航指针、自动化检查、code-review 技能所执行的编码规范、引导文件、工具链。机械性错误沉淀为确定性检查，需要判断的地方沉淀为编码规范。下一次构建从更好的环境起步。

### 上下文卫生

把第 1～3 步保持在**一个不中断的上下文窗口**里（在 to-tickets 之前不要压缩、不要清空），让盘问、规格和工单建立在同一套思考之上。每个 implement 随后从工单出发重新开始。retro 要在它所回看的那次会话里跑，趁还没清空；清空之后，就让它指向那次会话的日志。

这里的上限是**智能区**：模型仍能敏锐推理的那个窗口（在最先进的模型上约 150k tokens）。如果会话在 to-tickets 之前就接近上限，别在退化状态下硬撑；在最近的一个阶段边界处压缩上下文，然后继续（见「阶段边界」）。

## 上匝道

生成工作的起始处境，随后并入主流程。

- **缺陷和需求越堆越多** → **triage 技能**。它让议题流经分诊角色，产出可供代理处理的议题，再由 **implement 技能**接走。

  分诊只针对**不是你创建的**议题：缺陷报告、外部进来的功能需求、任何未经加工送来的东西。to-tickets 产出的工单已经可供代理处理，**不要对它们做分诊**。

- **有东西坏了** → **diagnosing-bugs 技能**。专治难啃的：第一眼看不出的缺陷、时有时无的偶发失败、在两个已知良好状态之间悄悄混进来的回归。它在拿到一个**紧密反馈回路**（一条已经能对*这个*缺陷变红的命令）之前拒绝做理论推演，然后用回归测试来修复。修复到位后，在同一次会话里跑 **retro 技能**，问一问本来什么能防住这个缺陷；如果真正的发现是根本没有好的接缝能把它固定住，那就是 **improve-codebase-architecture 技能**的活。

- **一件庞大而迷雾重重的事**（全新项目或巨型功能构建，大到一次会话装不下） → **wayfinder 技能**，这是几条流程里对认知要求最高的一条。当从这里到目的地的路还看不见时，它在议题跟踪器上画出一张由**决策工单**构成的**共享地图**，一次解决一张，产出的是**决定，不是交付物**，直到迷雾退去、路变清楚。grill-with-docs 打磨的是你一次会话里把握得住的想法，wayfinder 针对的是你把握不住的那个；它更慢、更密，只留给这种情况，绝不要用在范围明确的功能上。

  地图清晰之后，**它只交接，不构建**：在 **to-spec 技能**处并入主流程，由后者把地图上相互关联的决定收敛成可构建的计划，再照常走 to-tickets 和 implement。把地图直接接到 implement 会跳过这次收敛、丢掉关联细节，所以只有当这件事最终被证明确实很小时，才直接去 implement。

## 代码库健康

不是功能开发，只是日常维护。

- **improve-codebase-architecture 技能**：手头有空、想让代码库保持适合代理操作时随时跑。它找出**加深机会**；挑中一个就会*生成一个想法*，你可以把它带进主流程的 grill-with-docs。它是负责勘察候选者的；**codebase-design 技能**（见下）则是设计所选那一个的工作台。

## 底层的词汇

两份由模型调用的参考资料，运行在其它技能*之下*，各自是其词汇的单一事实来源。问题出在**词**而不是流程上时，直接取用它们；或者让上面的技能把它们拉进来。

- **domain-modeling 技能**：打磨项目的*领域*语言——质疑含糊的术语，拆解超载的词（比如「account」同时干三份活），把难以逆转的决定记录成 ADR。它是 grill-with-docs 会主动带着你做的那套功课，用来让 `GLOSSARY.md` 保持为一份干净的词汇表。
- **codebase-design 技能**：深模块的词汇（模块、接口、深度、接缝、适配器、杠杆、局部性），用来设计一个模块的*形状*：在干净的接缝处，把大量行为放到小接口后面。tdd 和 improve-codebase-architecture 都用这套词汇。

## 阶段边界

**阶段**是会话内的一块工作：盘问、实现、验收。在两个阶段之间的**边界**上，你有五个选项，在它们之间做选择是整张地图里最模糊的决定：

- **继续**：留在原地。不花代价，也不丢东西。
- **清空上下文**：这里没有任何东西对下一步重要时，清空窗口重开会话。
- **handoff 技能**写出一份可携带的 Markdown 文件。范围很窄：只用于**新的运行环境**、**新的目录**、**同事**，或者在**阶段中途**把侧任务分叉出去。它换来的是可携带性。
- **子代理**：把一个范围收得很紧的任务送到它自己的窗口，再拿一份报告回来。
- **压缩上下文**：把当前上下文压成摘要并用它开新会话。它是**默认选项**，位于决策树的底部，而不是第一个伸手去拿的。

读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 看那棵按顺序排下来的决策树：五个问题、每个分支背后的理由，以及为什么一手来源的代价让**继续**成为要最先判掉的一项。决定要**在**边界上做；阶段中途，要么继续，要么把其余部分拆成子代理。

## 独立使用

完全不在主流程上。

- **grill-me 技能**：和 grill-with-docs 一样不留情面的访谈，但**无状态**：不在本地保存任何东西，也不建 `GLOSSARY.md`。**不在工作目录里工作**时（打磨一个计划、一个设计、一篇文字，任何底下没有仓库的东西）用它。如果你在工作目录里，就改用 grill-with-docs：同一套访谈，还留下书面记录，严格来说更好。
- **grilling 技能**就是访谈原语本身：轮次、前沿，事实是代理的活，决定是你的。grill-me 和 grill-with-docs 是两个有名字的入口，triage、wayfinder 和 improve-codebase-architecture 内部都会跑它。只有当你想要这场访谈本身、不想要外面任何包装时，才直接取用它。
- **prototype 技能**是一个小小的、用完即弃的程序，用来回答一个设计问题：这个状态模型感觉对吗，或者这个界面该长什么样。用完即弃是对代码怎么写的一条约束，而不是要毁掉它的承诺：答案会融进真实代码，原型本身则作为**一手来源**保留在从 main 分出的 `prototype/<name>` 分支上，并从实现议题指向它。它是主流程第 2 步里的那段绕道，但当某个设计问题很难在纸上敲定时，随时可以取用。
- **research 技能**：把阅读的跑腿活交给一个**后台代理**：它对着**一手来源**调查一个问题，然后在仓库里留下一份带引用的 Markdown 文件。它阅读的时候你继续干活。它产出的文件是要*带进*主流程、交给 grill-with-docs 的，因为调研是给思考喂料，而不是替代思考。
- **to-questionnaire 技能**在卡住你的东西不在你脑子里、也不在代码库里，而在**别人脑子里**时出场：它给对方写一份问卷去填。它是 grill-me 的反面：不是就主题访谈你，而是就**这次投递**访谈你（要发给谁、你需要收回什么），把问题对准那道缺口。收回来的是给 grill-with-docs 或 to-spec 的素材。
- **wizard 技能**针对只有**人类**才能做的步骤：开通基础设施、配置凭据或 CI 密钥、在陌生的第三方仪表盘里点来点去、跑一次性的迁移或切换。它生成一个交互式 bash 脚本，逐个打开 URL、把每个值采集回来，并写进 `.env` 和 GitHub secrets，于是这套流程不再是你每次都要向代理重新解释的东西。它是模型调用式的，代理一撞上只有你能通过的那堵墙就会想到它。如果代理自己就能做，就应该自己做；这个技能是给人类确实还在回路里的场合。
- **wait-what 技能**是一条没落地的消息的矫正手段。在对话中途、在任何其它技能内部使用：代理会补上你当时缺失的上下文，用平实的话、用 `GLOSSARY.md` 里的词汇，把它刚说过的话重新讲一遍。它是事后补救；grill-with-docs 是事前的解药，因为早早商定的共同语言才是让行话压根不出现的东西。
- **teach 技能**：在多次会话里学一个概念，把当前目录当作一个有状态的工作区。
- **writing-for-agents 技能**是「怎么写代理要读的文档」的参考资料：技能、AGENTS.md、被引用的文档。

## 前提条件

**setup-matt-pocock-skills 技能**：在你第一次跑工程流程之前运行，用来配置其它技能所假定的议题跟踪器、分诊标签和文档布局。议题跟踪器可以是 GitHub Issues 或本地文件，按该技能的配置来；自定义跟踪器也能用。
