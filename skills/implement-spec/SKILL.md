# 按规格实现

前提：你手上有一份规格说明，并且它已经配好了工单，说明各部分该怎么落地。议题跟踪器（GitHub Issues 或本地文件）按 setup-matt-pocock-skills 技能的配置来用；如果仓库还没做过这项配置，先请用户运行 setup-matt-pocock-skills 技能。

目标：在一条**集成分支**上把整份规格实现完，并按议题跟踪器收尾工作的方式逐张解决工单。

工单不是一串直线式的步骤，而是一张带阻塞关系的**任务图**。这意味着任何时刻都存在一批不被任何未完成工单阻塞、随时可以领取的工单，称为**前沿**。

协作原则：

- 每个子代理都用全新上下文启动。
- 与子代理之间尽量少往来，主要靠**上下文指针**沟通：指向规格说明、工单、调研笔记和既往提交的引用即可。能通过指针拿到的信息，不要再复述一遍。

## 步骤

1. 读规格说明和全部工单，先弄清任务图的全貌。

2. （可选）派**探查子代理**去做工单要求的探查——相关的代码库文件或外部文档。要确保探查子代理能保存文件：它应当把 Markdown 笔记存到仓库之外、所有后续子代理都能访问的某个目录里。这样**实现者子代理**就能专注于实现，不必分心做探查。

3. 建集成分支。如果议题跟踪器是通过 PR 收尾工作的，或者用户要一个 PR，就在第 5 步第一次合并之后再开草稿 PR（一个还没有比 main 多出任何提交的分支是开不了 PR 的），并标注它会关闭这份规格说明和这些工单。

4. 用**实现者子代理**实现每张工单，每张工单各在自己的工作树、自己的分支上。**实现者子代理**应尽可能放到后台运行，以获得最大的并发度。每个实现者子代理都要：
   - 动手之前先确认自己的工作树是基于集成分支的，如果不是，就重置到集成分支上；
   - 用 tdd 技能把这张工单实现出来；
   - 在报告完成之前，把集成分支的最新提交合并进自己的分支。

5. 一个**实现者子代理**完成后，用**合并子代理**把它的成果合并到集成分支。

6. 如果这次合并改变了可领取工单的**前沿**，就再派几个**实现者子代理**去做新解锁的工单，保持最大的并发度。

7. 等所有工单都完成后，在集成分支上用 code-review 技能评审。用一个**实现者子代理**把代码评审提出的所有问题一次性修完。

8. 如果存在草稿 PR，就把它标记为可供评审。否则，按议题跟踪器收尾工作的方式逐张解决工单，并向用户报告集成分支。

9. 清理掉所有**实现者子代理**的工作树。
